## 1. 项目背景与目标

### 1.1 背景

医药公司需要将市场管理服务（等级医院开发与管理、商业公司开发、竞品与终端调研、医务人员/药店店员访谈、宣传服务等）以任务形式外包。平台承接这些任务，通过**定向分派**或**任务大厅公开接单**两种方式交给 C 端个人用户执行，对执行成果进行**审核、归集、结算、打包上报**。

### 1.2 目标

- **一期**：打通「任务发布 → 任务接收 → 成果提交 → 审核 → 归集 → 报告打包」的完整闭环，两端（运营平台 + 微信小程序）上线。
- **二期**：接入医药公司自助发任务、团队/公司组织管理与组织内审核、支付结算。

### 1.3 范围界定（一句话）

> 一期只做「任务发放、收集、报告整理」；**支付、医药公司发布任务、组织管理全部在二期**，一期仅在数据模型与接口上做预留。

## 2. 术语表

| 术语 | 定义 |
|---|---|
| 项目（Project） | **对外**的交付/结算单元，通常对应委托方（医药公司）的一单业务；一个项目可归集多个任务，一个任务可归集到多个项目（多对多） |
| 任务（Task） | 平台运营端发布的**对内**服务事项，分**周期性任务**与**定额任务**两类 |
| 周期性任务 | 按月周期执行的任务（如巡店、等级医院/商业公司管理采集），**单用户单月仅可提交一次** |
| 定额任务 | 限时限量的任务（如问卷/访谈调研），在指定时间范围内需完成指定份数，**单用户单月可重复提交** |
| 服务项目 | 结算单三级结构：**类型 / 项目 / 任务**，如「医院管理 / 等级医院 / 等级医院管理」（与「项目」实体不同，仅为结算分类） |
| 费用标准 | 任务计价：**单位 + 单价**（如「家/月，3000 元」）；任务金额仅对内，与项目对外金额不挂钩 |
| 执行要求 | 任务应完成的：**执行数量 + 执行标准** |
| 任务实例（Assignment） | 任务落到某个 C 端用户后形成的执行关系（来源可为运营定向分派，也可为用户在任务大厅自行接单） |
| 成果（Submission） | C 端用户针对一个对象（一家医院/药店/商业公司）提交的一份采集表/问卷 |
| 审核 | 运营端对成果的通过/驳回操作 |
| 归集（Aggregation） | 把某用户在某任务下所有「审核通过」的成果汇总为结算清单 |
| 结算单 | 归集产物：数量 × 单价 = 费用金额 |
| 报告 | 归集后按医药公司维度打包生成的交付物 |
| 每月发放额度 | 单用户单月实际**发放**金额的上限（默认 20000，可由运营调整）；与接收/完成任务金额无上限无关 |
| 个人任务津贴 | 应发金额中超出每月发放额度而**未发放**的部分，累计入个人账户，顺延至下月发放 |

## 3. 角色与两端职责

### 3.1 角色

| 角色 | 说明 | 归属端 |
|---|---|---|
| 运营人员 | 平台内部运营，负责发任务、定向分派/发布任务大厅、审核、归集、报告、判定任务完成 | 运营平台 |
| 审核员 | 运营人员中的审核角色（可复用 RBAC 权限控制） | 运营平台 |
| C 端用户 | 执行任务的个人用户（一期仅支持个人） | 微信小程序 |
| 医药公司 | 任务委托方（一期不直接操作平台，二期开放） | —— |

### 3.2 两端职责划分

| 功能 | 运营平台（`frontend/web`） | 微信小程序（`frontend/app`） |
|---|---|---|
| 微信登录 | —— | ✅ 微信登录（复用 `wx_mini_service`） |
| 任务发布/管理 | ✅ 一期唯一发布入口 | ❌ 仅查看 |
| 任务模板管理 | ✅ 配置采集字段/单价/标准 | —— |
| 任务分派 | ✅ 定向指派 / 发布任务大厅 | ❌ 主动接单 |
| 接收任务 | —— | ✅ 从任务大厅自行接单 / 接收定向指派 |
| 成果提交 | —— | ✅ 填采集表/问卷 |
| 成果审核 | ✅ 通过/驳回 | ❌ 只查看审核结果 |
| 归集/结算 | ✅ 生成结算单 | ❌ 只查看我的结算 |
| 报告打包 | ✅ 生成并导出 | —— |
| 项目/任务归集 | ✅ 维护项目、把任务归集到多个项目、判定任务完成 | —— |
| 发放额度配置 | ✅ 配置每月发放额度（默认 2 万） | ❌ 只查看我的发放/津贴 |
| 我的任务/收益 | —— | ✅ 列表 + 详情 |

> **结论**：一期「写操作」集中在运营端，「读 + 提交成果」在小程序端，职责清晰、无重叠。

- ❌ 财务发票、税务

## 5. 核心需求详述

### 5.1 任务模板

任务的采集字段高度异构（医院开发 vs 调研问卷 vs 宣传服务字段完全不同），因此**任务必须绑定一个「模板」**，由模板驱动小程序端的动态表单与运营端的审核视图。

- 模板要素：任务类型、**任务分类（周期性/定额）**、服务项目三级（类型/项目/任务）、单位、单价、执行数量、执行标准、字段定义（JSON Schema 描述采集字段）。
- 一期按附件固化 9 类任务模板（见 §5.2），运营端可改单价/标准，**字段结构一期由开发配置**（不做在线表单设计器）。

### 5.2 任务类型清单（来自附件模板）

| 任务号 | 任务类型 | 采集/提交对象 | 是否必选 |
|---|---|---|---|
| 1-4 | 空白市场开发采集 | 等级医院/基层医疗/民营医疗/零售药店 | 否 |
| 5-17 | 等级医院管理采集 | 等级医院/基层/民营/零售药店（按月） | 是 |
| 18 | 空白商业开发采集 | 商业公司 | 否 |
| 19-21 | 商业公司管理采集 | 商业公司 | 是 |
| 22-26 | 竞品与市场信息调研 | 竞品/市场 | 否 |
| 27-30 | 终端信息调研 | 等级医院/基层/民营/零售药店 | 否 |
| 31-34 | 医务人员访谈问卷调研 | 临床用药/产品认知/学术需求/患者反馈 | 是 |
| 35-38 | 药店店员访谈问卷调研 | 推荐习惯/产品认知/培训需求/顾客反馈 | 是 |
| 39-44 | 宣传服务 | 户外宣传/互联网宣传 | 是 |

> 结算单统一结构：`序号 | 服务项目(类型/项目/任务) | 费用标准(单位/单价) | 执行要求(执行数量/执行标准) | 实际执行(数量/费用金额)`。

#### 任务分类

任务按执行与提交方式分为两类：

| 分类 | 定义 | 提交约束 | 典型示例 |
|---|---|---|---|
| 周期性任务 | 按月周期执行、可长期承接 | **单用户单月仅可提交一次** | 等级医院/商业公司管理采集（巡店）、宣传服务 |
| 定额任务 | 限时限量，指定时间范围内需完成指定份数 | **单用户单月可重复提交** | 竞品/终端调研、医务人员/店员访谈问卷 |

### 5.3 任务发布、项目归集与分派（两种模式并存）

1. 运营端创建任务（选模板 → 填周期/单价/标准/执行数量 → 选任务分类 → 选择分配方式）。
2. **项目归集**：任务可归集到一个或多个「项目」；项目对外、任务对内，**项目金额与任务金额不挂钩**（项目按医药公司维度结算，任务按对内单价 × 数量计价）。
3. 分配方式二选一：
   - **定向分派**：指定 C 端用户（支持按用户 / 批量 / 撤销），发布后仅被指定用户在「我的任务」中可见并接收。
   - **公开大厅**：不指定用户，发布后进入任务大厅，所有 C 端用户可浏览并**自行接单**（定额任务受执行数量限量约束；周期性任务不限总份数）。
4. 任务发布后，接单成功的用户进入执行；未接满的定额任务持续在大厅展示直至名额接满或超出限定时间范围。

> **任务完成由运营判定**：由于一个任务可归集到多个项目，任务是否「完成」不依赖系统自动截止，而由运营人员手动判定（标记任务完成/关闭）。

### 5.4 任务接收与提交约束

- **不限制接单数量**：用户可同时接收任意数量的任务，系统不再做「累计接收金额/数量」的拦截。
- 提交约束按任务分类区分：
  - **周期性任务**：单用户单月仅可提交一次（同一任务同一月份重复提交被拦截，提示「本月已提交」）。
  - **定额任务**：单用户单月可重复提交，仅受任务总执行数量的限量约束（先到先得）。

### 5.5 成果提交

- 一次提交 = 一个对象（一家医院/药店/商业公司）× 一份采集表。
- 支持草稿暂存；驳回后可修改重新提交（保留历史版本）。

### 5.6 审核

- 审核维度：必填完整性、标准符合性、真实性抽查。
- 操作：通过 / 驳回（必填意见）。

### 5.7 归集、报告与任务完成

- **任务完成**：由于任务可归集到多个项目，任务「完成」由运营人员手动判定（标记完成/关闭），不依赖系统自动截止。
- 归集条件：任务完成后，对「用户 × 任务」下所有审核通过的成果，按结算单结构汇总数量、计算金额。
- 报告：按医药公司维度打包（汇总各任务类型完成量 + 结算金额 + 明细附件）。

### 5.8 成果提交的 AI 智能体检查（接口预留）

- 一期成果提交走「规则校验」：必填完整性、字段格式、数值范围。
- **预留 AI 检查扩展点**：后续在 C 端提交任务时，接入智能体对提交内容做检查（照片真实性、数据合理性、异常识别、自动预审）。
- 一期落地：提交接口预留 `checker` 抽象与 `ai_check_status / ai_check_result` 字段，AI 检查器以可插拔方式接入，**不影响一期主流程**。

## 6. 发放规则（重点）

### 6.1 规则定义

| 概念 | 说明 |
|---|---|
| 每月发放额度 | 单用户单月实际发放金额上限（默认 20000，运营可调为 10000 / 20000） |
| 累计应发金额 | 该用户本月已归集（审核通过）成果的金额之和（**无上限**） |
| 待发金额 | 本月应发金额 + 上月个人任务津贴余额 |
| 实发金额 | 本月实际发放金额 = `min(待发金额, 每月发放额度)` |
| 个人任务津贴 | 待发金额超出每月发放额度的部分，累计入个人账户，顺延至下月发放 |

### 6.2 规则逻辑（示例）

> 用户每月发放额度 = 2 万；本月完成任务的应发金额 = 3 万；上月津贴余额 = 0。

1. **接收/完成任务无上限**：不限制接单数量，也不限制任务金额，用户可完成任意金额的任务。
2. **待发金额** = 本月应发 `3 万` + 上月津贴 `0` = `3 万`。
3. **实发金额** = `min(3 万, 2 万) = 2 万`。
4. **津贴累计**：剩余 `1 万` 记入个人任务津贴，顺延至下月发放（优先于下月新增应发金额）。

### 6.3 一期落地口径

- 一期**只计算、只展示**：累计应发金额、每月发放额度、实发金额、个人任务津贴，**不做实际打款**。
- 结算单中金额字段在一期即为「应发金额」；「实发金额」「津贴」字段预留，二期支付时写入。

## 7. 二期功能规划（预留）

| 功能 | 说明 | 预留设计 |
|---|---|---|
| 医药公司任务发放平台 | 医药公司自助发任务、验收 | `task.publisher` 抽象为「发布者」；预留外部租户 |

| 组织架构 | 团队/公司多级 | `C 端用户` 抽象为「执行主体」，个人/团队/公司为子类型 |

## 8. 待确认项（评审时决策）

1. 任务分配方式：一期已确定「定向分派」与「任务大厅自行接单」两种并存；创建任务时的**默认分配方式**待评审确认。
2. 发放周期是自然月还是「任务周期」？（一期默认自然月）
3. 个人任务津贴是否可跨多周期累计？有无上限？（默认可累计、无上限，待评审确认）
4. 每月发放额度是否可按用户差异化配置，还是全局统一默认 2 万？
5. 报告格式是 Excel 打包还是在线看板 + 导出？
6. 审核是否需要「初审 + 复核」两级？
7. 任务「完成」由运营判定的具体口径：完成 = 成果全部审核通过，还是运营主观判定即完成？

## 9. 非功能需求

- 性能：成果提交列表、审核列表支持分页与筛选，单接口 P95 < 500ms。
- 权限：复用现有 RBAC，运营端按菜单/按钮授权。
- 审计：任务/成果/结算的关键操作留痕（复用 `sys_operation_log`）。
- 数据安全：机构与人员信息脱敏展示，敏感字段按角色控制。
- 兼容：小程序覆盖微信平台（复用 `@dcloudio/uni-app` + `uni-mp-weixin`）。
