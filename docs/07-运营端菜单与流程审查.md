## 2. 端到端流程现状与断点

运营视角的真实链路（含断点）：

```
项目(选关联任务) → 发布项目 → 【生成 DRAFT 任务】→ 任务页发布/分派 → C 端接单提交
   → 任务审核（逐条弹窗）→ 通过即自动结算 → 结算单确认 → 生成月报 → 交甲方
```

断点位置（详见第 3 节）：

| # | 断点 | 运营感受到的现象 |
|---|---|---|
| B1 | 项目发布只产出草稿任务，任务页「搜索」无条件排除 DRAFT | 项目发布了，任务列表里找不到任务 |
| B2 | 任务无执行进度视图 | 不知道今天该催谁，只能靠翻成果页 |
| B3 | 审核逐条 720px 弹窗 + 二次确认 + 结果 alert | 30 条成果 ≈ 90 次点击 |
| B4 | 审核通过即自动结算（与手动归集规则还不一致） | 想「先审完再统一结算」做不到，也不敢批量点 |
| B5 | 报告页只读 raw JSON、无下载、无状态推进 | 最后一步「交甲方」回到手工，系统闭环断在这里 |
| B6 | 全模块无导出 | 财务/甲方要 Excel 只能截图 |
| B7 | 页面之间零跳转 | 看完成果想回到任务/机构，要重新搜 |

## 3. 问题清单

### P0 — 阻断或直接误导运营

**P0-1 项目发布产出草稿任务，而任务页搜索会隐藏草稿**
- `project/service.py:243` 发布项目时生成 `status="DRAFT"` 的任务实例；
- `task/index.vue:625` `handleSearch` 无条件追加 `exclude_status: "DRAFT"`（首次加载和点侧栏树不带此参数，所以只有「点搜索」后才消失）。
- 后果：运营「项目 → 发布 → 去任务页按项目搜」= 空列表。这是他判断"发布成功了没"的第一动作。
- 建议：删掉该参数；若确实想默认收起草稿，改为显式状态筛选默认值 `PUBLISHED` 并在搜索栏可见。

**P0-2 三个页面最重要的动作按钮，文案都是「新增」**
- `settlement/index.vue:21`、`member/index.vue:20`、`report/index.vue:22` 都传了 `create-text`，但 `components/tables/fa-table-header-left/index.vue` 的 Props **没有这个字段**（第 51–86 行），模板里第 18 行硬编码「新增」。
- 后果：运营看到「新增」不敢点（以为是新增一条结算单）；点开才知道是「归集结算 / 纳入成员 / 生成报告」。这是最容易修、感知最强的一处。
- 建议：给 `FaTableHeaderLeft` 补 `createText?: string`（默认「新增」）；或三处改成自定义插槽。

**P0-3 工作台「待处理」三张卡里只有一张是真待办**
- `dashboard/index.vue:423-426` 第三卡是 `d.settlement.total`，而后端 `dashboard/service.py:127` 的 `settlement_total` 是**全部状态结算单总数**，不是待确认数。
- 前两张卡的跳转也不带筛选：`to: "/market/task/submission"`（第 412 行）→ 落地是「全部状态」列表，而下方待审队列的跳转是 `?status=PENDING`（两处口径不一致）。
- 「进行中任务」只统计 `IN_PROGRESS`（`service.py:100-104`），漏掉最该催的 `PUBLISHED`（已发布没人接）和 `DRAFT`（未发布）。
- 建议：待办四卡改为**可行动的计数**：待审核成果(`PENDING`)、待发布任务(`DRAFT`)、待确认结算单(`CALCULATED`)、待审产品(`pending`)，每张卡跳转都带 `?status=`；工作台是运营每天第一个页面，它错了等于导航错了。

**P0-4 流程终点（月报）没有任何可用出口**
- `report/index.vue` 只有一个「详情」，详情里 `<pre>` 打印 `summary` JSON 原文（scout 复核），没有下载、没有「标记已提交」；
- 菜单里给了 `module_market:report:update/delete`，但页面完全没用到；
- 后果：`report.status` 的 `GENERATED → SUBMITTED` 没有写入路径，运营建完报告就卡死。
- 建议：详情加「下载（xlsx/pdf）」「标记已提交」；短期若来不及做导出，至少不要展示 raw JSON（先渲染成表格）。

### P1 — 每天多花时间 / 容易出错

**P1-5 成果审核没有批量，也没有「快审」**
- `submission/index.vue` 无勾选列、无批量按钮；行内只有「详情」「审核」，审核是 720px 弹窗（`handleReviewSubmit` 里还有 `ElMessageBox.confirm` 二次确认 + 成功后 `ElMessageBox.alert` 展示结算结果）。
- 单条通过 = 打开 → 选「通过」→ 确认 → 关 alert，4 次交互；一期量级（几十条/月/人）下这是主要时间成本。
- 建议：列表加勾选 + `批量通过`（后端已有 review 接口，循环或新增 batch）；行内 `快速通过` 免弹窗（驳回才弹，因为要填意见）。

**P1-6「审核即结算」把两个节奏绑死了，且和手动归集规则冲突**
- 审核通过 → 自动调 `SettlementService.settle(require_completed=False)`（`payout/service.py:110-124` 的注释明确"审核是业务真实终点，不看任务状态"）；
- 但运营手动「归集结算」要求任务已 `COMPLETED`（同文件 123 行）。
- 后果：同一件事两条路径、两套前置条件；运营无法「本月全部审完再一次性结算」，且每次审核都被结算弹窗打断。
- 建议：加一个设置项（`sys_param`）`market.auto_settle_on_approve`（默认开），关掉后走"月末统一归集"；两条路径的前置条件在 UI 上写清楚。

**P1-7 所有跨实体选择器都是「前 100 条本地下拉」**
- 分派选人 `task/index.vue:564`、审核筛选 `submission/index.vue:324-326`、结算选任务/用户 `settlement/index.vue:252-253`、额度选用户 `payout/index.vue:439`、成员选用户 `member/index.vue:211`、报告选项目/模板 `report/index.vue:210-211`。
- 后果：C 端成员或任务超过 100 条后，**分派时选不到人**（这是功能不可用，不只是体验问题）；同名用户也难区分（只有 `name`）。
- 建议：改用 `filterable remote` + 后端 `keyword` 搜索；分派选人列表接 `market_member`（只列启用的 C 端成员），显示 `姓名（手机号）`。

**P1-8 任务页看不到「执行进度」**
- `task/index.vue` 表格只有「接收人数」一列；没有"本月已提交/已通过/待审核"。
- 后果：运营的日常动作是"这个任务这个月还差几个人"，现在必须去成果页按任务筛。
- 建议：任务列表加三列（或一格 `3/5 已提交 · 2 通过`），行内加「查看成果」直达审核页 `?task_id=`。

**P1-9 页面之间几乎没有跳转，关键信息是裸 ID**
- 全 market 模块唯一的 `router.push` 是 `submission/index.vue:316`（"查看结算单"）；
- 结算列表「任务ID」直接渲染 `task_id`、图片归集「来源成果」渲染 `#submission_id`、任务抽屉分派子表的「操作」列在非 `PENDING` 行是**空白单元格**。
- 建议：把这几处做成链接（任务详情抽屉 / 成果详情）；任务抽屉分派行补「查看成果」。

**P1-10 全模块零导出**
- `grep 导出` 在 `views/module_market/` 无命中。
- 结算单、发放结果（应发/实发/滚存）、成果明细都需要给财务与甲方。
- 建议：结算单 + 发放结果各加一个「导出 Excel」，用现有 `useImportExport`。

**P1-11 任务状态流转的三个小坑**
- `task/index.vue:683` `STATUS_FLOW` 缺 `SETTLING`：处于该状态的任务既不显示「状态流转」按钮、弹窗里也无可选值（该状态本来无写入路径，属死状态，应删或补齐）；
- 弹窗「当前状态」是 disabled input 绑枚举原值，显示 `PUBLISHED` 而不是「已发布」；
- `SETTLED → ARCHIVED` 要在两次弹窗里各点一次，无提示「归档是收尾动作」。

**P1-12 发放管理默认落在错误的 tab**
- `payout/index.vue:175` `activeTab = ref("result")`，而运营第一个月的第一个动作是「配额」。
- 建议：无配置数据时默认 `config`；或结果为空时给一句「尚未归集，先去结算管理」。

## 4. 建议：运营菜单重组

原则：**高频在前、有名字的目录不重名、配置件沉底、每个叶子只属于一个目录**。基座菜单照旧靠 RBAC 屏蔽。

| 现在 | 建议 | 理由 |
|---|---|---|
| 运营工作台 > 工作台概览 | **运营工作台**（待办中心） | 每天第一个页面，内容从"看板"改为"待办"（P0-3） |
| 任务管理 > 任务 | **任务执行 > 任务跟进** | 运营在这里做的是"跟进"，不是"管理任务定义" |
| 任务管理 > 任务审核 | **任务执行 > 成果审核** | 名字直接说动作；和"任务"并列在同一个目录下，顺序放审核在前（更高频） |
| 任务管理 > 任务目录 | **配置 > 任务目录** | 分类/模板/采集表是配置件，一次配好、长期不动 |
| 项目管理 > 项目 / 报告管理 / 医药公司 | **项目管理 > 项目 / 月度报告 / 医药公司** | 「报告管理」→「月度报告」，带上节奏感 |
| 发放管理 > 结算管理 / 发放管理 | **结算与发放 > 结算单 / 发放额度 / 发放结果** | 拆掉与父目录同名的叶子；「发放结果」独立成页（现在藏在第二个 tab 里） |
| 机构管理 > 机构管理 / 图片归集 | **主数据 > 机构 / 图片归集 / 产品库 / C 端成员** | 四级目录收成一个"主数据"目录；产品库提上来（每日待审） |
| 产品库（叶子） | 同上 | 不再与目录同层 |
| 成员管理（叶子） | 同上 | 同上 |

建议的最终侧栏（运营角色）：

```
运营工作台
任务执行        → 成果审核 / 任务跟进
项目管理        → 项目 / 月度报告 / 医药公司
结算与发放      → 结算单 / 发放额度 / 发放结果
主数据          → 机构 / 图片归集 / 产品库 / C 端成员
配置            → 任务目录
系统            → 公告 / 工单 / 用户
```

一次性成本：改 `backend/sql/sys_menu.json`（或后台菜单管理里拖）+ 重配角色权限 + 三处 `component_path` 不变。**不需要改任何页面代码**，纯配置。

## 5. 建议：流程改造三件事

1. **工作台变待办中心**（P0-3）：四张可行动卡 + 带 `status` 的跳转；下方保留「待审队列」（已有）。这一个改动决定运营每天 80% 的路径。
2. **审核工作台**（P1-5/P1-6）：勾选 + 批量通过；行内「快速通过」；审核后不再弹结算 alert，改 toast + 内联「查看结算单」；`auto_settle` 开关。
3. **月末交付闭环**（P0-4/P1-10）：结算单批量确认 → 按「项目 × 模板 × 月份」生成报告 → 报告可导出/下载 → 标记已提交；发放结果可导出。

## 7. 未验证项（需要跑起来确认）

- 审核通过后自动结算的实际弹窗文案与金额口径（仅读代码，未实际点过）；
- `settlement` 状态列首访 `—` 是否真的复现（取决于字典缓存时序）；
- 任务页「点搜索才隐藏草稿」的确切复现路径（需浏览器确认首次加载与搜索后的差异）。
