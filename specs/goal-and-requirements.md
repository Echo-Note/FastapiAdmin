# 医药市场管理服务平台 —— 产品目标与能力

> 本图谱由现有代码与 `docs/` 反向导入起草。除标注「未确认」处外，每条断言都有代码或既有设计文档佐证；`status: draft`，待人工评审后才转 `active`。

## 目标

把医药公司的市场管理服务（等级医院/商业公司开发与管理、竞品与终端调研、医务人员与药店店员访谈、会议与宣传服务）以外包任务的形式发出去，收上来可审核的采集成果，按「数量 × 单价」算出应发金额，最后按项目打包成可交付给甲方的月度报告。

平台是这件事的**全流程载体**：任务怎么发、谁怎么接、成果怎么审、钱怎么算、报告怎么交，都在一处留痕并可对账。

## 问题

- **采集字段高度异构**：等级医院开发、竞品调研、会议服务要填的东西完全不同。同一张表装不下，改一次业务就得改一次库。→ 表单结构必须随任务走，而不是随数据库表走。
- **执行者是分散的个人**：成果质量参差，需要逐份审核、驳回重提。→ 成果必须有版本与审核留痕。
- **结算不是「干了多少给多少」**：按人头月度控额，每人每月发放有上限、超出部分顺延下月。→ 结算与发放必须分层。
- **甲方要的是打包材料**：「这个项目这个月做了多少、给多少钱」。→ 成果 → 结算 → 报告要能按项目聚合。
- **原本散落在 Excel 与微信里**：无留痕、无审核、无法对账。

## 使用方

| 使用方 | 入口 | 权限面 |
|---|---|---|
| 运营人员（含审核员） | Web 端 `frontend/web` | 平台唯一的业务写入口：维护任务目录与项目、发布与分派任务、审核成果、跑结算、生成报告、配置发放额度 |
| C 端个人用户（一线代表） | 微信小程序 `frontend/app` | 只读 + 提交：逛任务大厅接单、看我被分派的任务、按动态表单提交成果、看我的收益与津贴 |
| 医药公司（委托方） | 无入口 | 当前不直接操作平台，由运营端代为发布与上报 |

「项目对外、任务对内」：项目是交付与结算单元，任务是内部执行单元，两者的金额不互相推导。

## 能力

代码现在就在做的事：

1. **任务目录三级**：一级分类 → 二级模板 → 三级任务。模板与三级任务各自用 JSONB 配置承载计价单位、单价、计价方式、执行标准、执行人员要求、提交规则，以及一份动态采集表单（`form_schema`，有序分节）。**有三级任务的模板不承载采集表单**——表单由三级任务自包含。
2. **项目与任务单元关联**：项目归属一个医药公司，项目上挂「任务单元」：有三级任务的模板挂其三级任务，无三级任务的叶子模板直接挂模板。发布项目时按所选任务单元批量生成任务实例。
3. **任务发布与分派**：发布只做状态流转；分派与发布解耦。两种分配方式——运营定向分派，或放进公开大厅让用户自行接单。任务的 C 端显示名自动生成为 `{项目}-{二级模板}[-{三级任务}]`。
4. **成果提交与审核**：一次提交 = 一个采集对象（机构/医务人员/患者/会议）× 一份采集表单，按月份归属；驳回可改，版本 +1。
5. **归集结算**：按「任务 × 用户 × 月份」汇总审核通过的成果，单价 × 数量算出应发金额，生成结算单与按「一级分类名 + 二级模板名」归组的明细。
6. **发放额度与津贴账户**：配置每个用户每月的发放上限（默认 20000），并提供个人津贴账户与明细的查询展示。
7. **月度报告**：按「项目 × 二级模板 × 月份」聚合当月审核通过的成果生成报告提交甲方；`template_id` 为空表示全项目汇总。
8. **机构主数据与图片归集**：机构是采集对象主体；机构主数据由 C 端提交时归集产生（按名称查重复用），提交时上传的门头照/内景照/打卡照按机构归集，可回溯到来源成果。
9. **运营看板**：market 域自己的聚合概览（任务/成果/结算统计 + 基础数据计数）。
10. **平台基座（复用上游 FastapiAdmin）**：RBAC 菜单/按钮权限 + 部门维度行级数据权限、操作日志审计、后端菜单驱动的动态路由与多标签 KeepAlive、定时任务与存储工作流、代码生成器、AI 对话、SSH 运维、外部库只读 SQL 控制台。

## 非目标

以下是被明确排除的，不是「还没想」。

- **支付/打款**：结算只算应发金额并展示，不动账户余额、不发起支付。`market_settlement.paid_amount` / `pay_status` 是预留列，没有写入路径。
- **医药公司自助发布任务 / 多租户 SaaS**：平台没有租户概念（代码中零 `tenant` 实现），医药公司没有账号与入口。`REQUIREMENTS.md` 描述的 SaaS 多租户与三层数据隔离是**未实施的愿景**，不是本系统现状。
- **团队/公司组织管理与组织内审核**：任务直接派给个人用户，没有组织树内的多级审核。
- **财务发票与税务**。
- **对外服务项目价目体系**：不存在「服务项目类型/服务项目/服务项目任务」三级价目表（`market_service_item` 等表在代码中零实现），对外报价不在本系统内。

> 未确认：上述后四项在 `docs/01-PRD` 里被排入「二期」。本图谱不记录版本与排期，此处只声明「现在不做」；它们是永久排除还是仅延后，需产品方确认。

## 原则

- **写入口唯一**：只有运营端（Web）产生业务写操作；C 端（小程序）只读 + 提交自己的成果。
- **表单随任务走**：采集字段是任务配置的一部分（JSONB 存储 + Pydantic 权威定义），前端 TS 类型只对齐、不做定义源；加字段不改表结构。
- **项目对外、任务对内**：项目是结算与交付单元，任务是执行单元，两者的金额不互相推导。
- **编号后端生成**：分类/模板/三级任务/公司/项目的编号形如 `{PREFIX}-{NNN}`，由后端原子分配，前端不提供输入框。
- **任务不携带配额**：任务没有名额或金额上限字段，接收行为是「幂等防重」而非「占名额」——用户能接多少取决于运营分派与大厅可见性。控额发生在发放环节，不是接收环节。
